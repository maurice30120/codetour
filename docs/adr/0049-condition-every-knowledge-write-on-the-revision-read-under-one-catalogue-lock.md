# Condition every Knowledge write on the revision that was read, under one catalogue lock

Spec #232 needs to repair a Knowledge Entry whose evidence no longer verifies: the entry is unreadable by design, nothing today rewrites it, and duplicating it under a derived name splits one durable piece of knowledge into two. It also needs two writers never to lose each other by interleaving. We decide that every Knowledge write runs in one critical section protected by a single catalogue lock — `.tours/.memory/knowledge/.catalogue.lock`, exclusive create with age-based takeover of a lock left by a crashed writer, the same primitive the Run State already uses — and that a write to an existing entry is conditioned on the Knowledge Revision the caller read (ADR 0048).

**What the critical section covers.** The entry file re-read, the comparison of its revision with `expectedRevision`, the second read of every cited evidence, the write of the staging file, and the publication. `knowledge_save` gains an explicit `mode`: `create` (default) keeps its whole current behaviour — validation order, multi-entry atomicity, publication by exclusive hard link — and `replace` rewrites one entry in full from the revision it read. `create` takes the same lock: an unlocked path is a path that will eventually be forgotten.

**Why the lock is catalogue-wide and not per entry.** The canonicalizer marker (ADR 0046) belongs to no entry: it records the engine identity that produced the catalogue's symbol fingerprints, and it is written at most once. A per-entry lock would therefore need a conditional second lock for the marker, and a lock that is sometimes taken is a lock that some path eventually skips. One lock over the catalogue is also enough: writes last milliseconds and two simultaneous consolidations on one workspace are not a use case, so serializing independent writes costs nothing measurable.

**Why readers take no lock.** Reads are the common path — discovery verifies every entry — and a read lock would serialize them against a writer for no benefit. Publication by atomic rename from a staging file inside the same directory already gives a reader the whole previous file or the whole new one, and `create` keeps its exclusive-link primitive as a redundant guard independent of the lock. A read never observes a half-written entry, whether or not a lock exists.

**Why publication renames instead of deleting.** A replace never deletes the previous file first: the rename is the single publication point, so a failure at any step leaves the previous entry readable in its prior state and no staging file survives. `create` cannot publish by rename — a rename would silently overwrite an existing entry — so it keeps the exclusive link, which is atomic and refuses an existing target.

**Why an absent revision is a conflict, not a validation error.** A `replace` without `expectedRevision` is not a malformed proposal; it is a compare-and-swap that cannot be satisfied. It sorts as `conflict` / `revision_conflict` and closes the run as `failed` / `conflict`, the same client vocabulary as an existing name, with a reason that points at the corrective action: re-read the entry, then retry. A stale token, an incorrect one and an absent one are one case, because all three mean the same thing: the writer does not know which bytes it is overwriting.

**Why `origin` became engine-only.** A file proof can carry `origin: symbol_fallback`, the engine's trace that it substituted an unresolvable symbol proof (spec #233). Accepting it from a caller let a client whiten a substituted proof or decorate a deliberate file proof with a fallback it never suffered. It is no longer an accepted input key; the engine alone writes it, and only on a substitution it actually performed. A rewrite neither adds nor removes that trace: it carries a historical `origin: symbol_fallback` verbatim onto a resulting `file` proof whose `(type, path, sha256)` is identical to the one that carried it, writes no origin on any other proof — a changed path or digest is a new proof — and refuses an unresolvable symbol instead of substituting one. An entry whose historical contract does not parse offers no historical proof to match, so the rewrite carries no trace.

**Why the lock primitive is a copy.** The lock is implemented inside `codetour-knowledge` as a copy of the Run State lock, deliberately not shared: the Knowledge package is the deterministic core and cannot depend on `codetour-mcp`, which depends on it. Two small copies of an exclusive-create-plus-age-based-takeover are the cost of keeping the dependency direction; consolidating them would require a third package for one file primitive.

**Consequences.** Two writers starting from the same revision produce exactly one published rewrite and one `revision_conflict`, whatever the interleaving. A catalogue whose canonicalizer marker differs refuses any write carrying a `symbol` proof, `replace` included, so repairing under a changed engine uses `file` proofs; the marker is never rewritten. A lock held beyond the timeout surfaces as an internal failure instead of an unconditional overwrite. The evidence stability re-check now runs inside the critical section, so it still guards against a third party moving a cited source file — a distinct threat from a second Knowledge writer.

Considered and rejected: a per-entry lock file (the marker belongs to no entry, so the lock would be conditional); write-then-verify (the losing writer overwrites bytes before discovering the conflict); delete-then-rename (a crash between the two leaves no entry at all); a monotonic generation counter instead of the file digest (a second state to persist, and it survives nothing that rewrites the entry by hand); locking readers (no gain over the atomic rename).
