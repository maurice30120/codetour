# Use in-process Tree-sitter with per-language rule packs, in a dedicated module, for dependency relations

Spec #92 wants the Targeted Context to carry a bounded dependency graph — callers, callees, class usages of a symbol, depth 1, with file:line evidence — because grep-plus-whole-file-reads dominate the token cost of a valid Tour. PR #135 ships only a regex-based symbol extractor (`packages/mcp-server/src/parsing/symbol-extractor.ts`), and spike #148 compared exactly two mechanisms for the graph: A — the `@codeflow-map/core` library, B — a minimal in-house graph on Tree-sitter/WASM. Spec #149 requires four languages: C#, Java, TypeScript, Python. The decision is **B**, and it settles the parsing-mechanism question of #114.

The engine is `web-tree-sitter` running in-process in Node, with prebuilt `.wasm` grammars from the `tree-sitter-wasms` distribution (which ships `tree-sitter-c_sharp.wasm`, `tree-sitter-java.wasm`, `tree-sitter-typescript.wasm`, `tree-sitter-tsx.wasm`, `tree-sitter-python.wasm`). No JVM, .NET runtime or Python runtime is embedded in the VSIX, and there is no network call at runtime. Resolution lives in per-language declarative packs registered in a shared engine; a pack that cannot prove a relation emits an explicit ambiguity site (`?` line with candidates and a targeted slice), never a guessed edge, and a language without a pack is `unsupported`, never a silently empty graph. The graph format is the one validated by the prototypes: `node`/`edge` (`kind: call|new|super`, `callType: direct|interface|super|new`)/`site`, statuses `resolved|heuristic|ambiguous|unresolved|unsupported`, BFS at depth 1 with `maxNodes/maxEdges/maxTokens`, extraction cached by (file, content SHA, language, analyzer version).

The engine and the packs ship as a **dedicated module** — its own package under `packages/` (named like `codetour-description-renderer`, e.g. `codetour-relation-graph`) exposing a pure `(sources, language) → graph` function plus the language registry. `codetour-mcp` consumes it through a thin seam and contains no Tree-sitter code of its own, so the regex spike can be replaced without touching the server's internals and each pack stays a small, reviewable, separately testable module.

## Considered options

- **`@codeflow-map/core` (piste A) — rejected on measured facts, not assumptions.** Version 1.0.3 (MIT, ~268 KB unpacked, deps `web-tree-sitter` + `minimatch`) supports TypeScript, JavaScript, TSX, JSX, Python and Go — not C# and not Java, two of the four required languages, so it cannot carry the spec alone. It embeds no grammars: it requires an externally assembled `wasmDirectory`, and the POC failed with ENOENT until `tree-sitter.wasm` from `web-tree-sitter` was copied next to the grammar files — the VSIX and standalone packaging burden remains ours either way. Its `buildCallGraph` resolves calls by name, which produces false edges on same-named methods across classes, aliases and overloads, and a call graph does not model `new` (class usage), inheritance or interface dispatch, which the edge contract above requires. Finally `analyzeDirectory` scans the whole project with no Git snapshot (SHA) semantics, which the Changes Tour needs.
- **repomap as the central mechanism (#114's alternative) — rejected**: it adds an abstraction layer over Tree-sitter without language breadth beyond it, and ts-morph was already disqualified as mono-language.
- **Embedded LSP (csharp-ls or similar) — rejected**: it would require a JVM and a .NET runtime inside the VSIX, and even Roslyn's call hierarchy is blind to interface dispatch, which must surface as ambiguity candidates.
- **A third-party MCP server for the graph — rejected**: the server already integrated into CodeTour stays the single exposure point to the agent; no new tool surface is added, and `getSymbolDependencyGraph` remains an internal abstraction, not a mandatory MCP tool.

## Consequences

- #148 is closed with this decision recorded; it supersedes the paper-only answer of #114, and the regex-based spike in `symbol-extractor.ts` (PR #135) is replaced by the TypeScript pack while preserving the existing `extractSymbols` contract for its consumers.
- #149 is decomposed into tickets #150–#156, each blocked by #148 until this decision landed: dedicated module (#150), packs TypeScript/C#/Java/Python (#151–#154), Targeted Context integration (#155), prototype absorption and tests (#156).
- The relations packet ships under the existing Targeted Context flag, off by default — ADR 0033 is unchanged: no new flag, no hybrid flag, and with the flag off the historical pipeline is provably identical.
- Token cost of the packet is tracked through the existing cost-tracking module so benchmark #118 can compare packets against the historical baseline; the go/no-go on enabling the flag stays with #118's measurements.
