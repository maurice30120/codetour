# Compare-and-swap Knowledge writes under one catalogue lock, keyed by a byte-digest revision

Spec #232 needs to amend an existing Knowledge Entry, not only create one. A filesystem offers a compare-and-swap for *creation* — a hard link fails when the target exists, which is what makes `create` safe today without any lock — but none for *replacement*: `rename` overwrites unconditionally, so two writers that both read revision R silently lose one addition. We decide that all three `knowledge_save` modes take one catalogue-wide lock (`.tours/.memory/knowledge/.catalogue.lock`, exclusive create plus stale reclaim, the pattern already used for the Run State), and that the revision token handed to `append` and `replace` is the SHA-256 of the entry file's complete bytes.

Why: the lock must span re-read, revision comparison and publish, and only a lock can close that window. It is catalogue-wide rather than per-entry because the `.canonicalizer` marker written by a symbol-proof save belongs to no single entry; guarding it with a second lock would make the first conditional, and a conditional lock is a forgotten lock. The token hashes the whole file rather than the body alone (which would miss an evidence change) or the contract alone (which would let an `append` land on a stale body); it needs no frontmatter field and no catalogue migration, and it is computable on an entry whose contract no longer validates, which is exactly what makes a repairing `replace` possible without ever serving an invalid body.

Considered and rejected: per-entry locks (leave the canonicalizer marker unguarded); replacing by `unlink` then `link` (exposes an instant where the entry is absent, and a crash in between destroys it); no lock plus a second read (the existing stability check guards a *third party* editing a cited source, a different threat from a second Knowledge writer); a revision counter persisted in frontmatter (needs a format migration for every existing entry); an HMAC keyed per workspace (removes the guessing oracle below, at the cost of key management judged not worth it for a local offline tool).

Consequence: `create` becomes serialized, a behaviour change on a shipped feature, and readers stay lock-free because publication is an atomic rename. `append` can never introduce the `insufficient_backing` warning — adding evidence on an already-cited path does not change the distinct-path count — so only `replace` can make it appear or disappear. The byte digest commits to the frontmatter, so a client that guesses a candidate frontmatter can confirm its guess; accepted, because the digest reveals no body, no cited path and no source fingerprint.
