# CodeTour research

Create a Project Tour for the user's objective. You own the overall decomposition and narrative; the CodeTour research harness answers individual questions, and the existing CodeTour MCP validates and writes the Tour. Keep the requested language for the Tour and your response.

1. Select the target workspace root. In a multi-root workspace, require the user to select one root before running anything. Resolve it to an absolute directory and use that same root for every research call and the MCP call. Check that the terminal, `codetour-research`, and `create_project_tour` are available. If the terminal is denied, the executable is missing, or the CLI reports a missing model key, inaccessible workspace, sandbox, or other preflight error, report the actual failure and stop; do not substitute an unrecorded exploration or claim success.
2. Turn the objective into a brief plan of functional questions that together explain the requested behavior. Each question covers exactly one mechanism or execution path, never several, and names the directories or files to examine (and any to exclude, such as `docs/` or `.tours/research-reports/`) when they are known; when they are not, first ask one short question that only locates the relevant files, then target the next questions with its answer; multi-mechanism questions have exhausted millions of tokens without a structurable result. Include its significant conditions and relationships, even when it crosses files. Choose the number and scope from the objective; questions may share code, but each should be understandable on its own. For example, to explain procedural memory, ask three separate questions: how a procedure is selected and executed, how a new procedure is tried and validated, and how it is persisted for later reuse. Delegate each substantial investigation **sequentially** using the installed CLI:

   ```sh
   codetour-research --workspace "$WORKSPACE_ROOT" --code --memory --output-file "$RESULT_FILE" "$QUESTION"
   ```

   For this CodeTour checkout, if `$WORKSPACE_ROOT/.tours/codetour-research` exists, run `"$WORKSPACE_ROOT/.tours/codetour-research" --output-file "$RESULT_FILE" "$QUESTION"` instead. It retrieves the local Mistral credential from the macOS keychain without printing it. For other projects, use the globally installed CLI above.

   Run the CLI as a background process with `--output-file` (`... & PID=$!`) and block on `wait $PID`, reading its exit status: a synchronous shell call is killed at its timeout (~300 s). Never start a second run on the same output file while the first is alive; the CLI refuses with `Run already active` (lock under `.tours/.log/locks/`). While it runs, follow `tail -f "$RESULT_FILE.progress" | jq -c '{phase,type,name,elapsedMs,inputTokens}'`; lines carry `phase` and counters, and `memory_unused` marks a run that ended with no `function_try` or `memory_run`. Events: (`plan` with the initial plan, `investigate`, `step` per tool call with truncated parameters and error, `consolidate`, `consolidation_result` with accepted/rejected functions and reasons, `end`, with elapsed time and token counts); the lock frees when the run ends; the result file itself is written only at the end, and stdout then carries only a compact summary (status, tokens, citation count, memory accepted/rejected, result path) — read details from the file with `jq`. The result has no `answer` key: read `.components`, `.relations`, `.entryPoints`, `.uncertainties`; `.callTrace` is an array and `.consolidationReport` an object, so query them in separate `jq` calls. Use a distinct result file for each call under `$WORKSPACE_ROOT/.tours/.log/q/` (create it first; the harness reads nothing there); inspect only the needed fields with `jq` and keep the full JSON out of the transcript. Check the exit status and stderr, including when no result file was written.

   Add one seeding question to the plan: ask for a reusable, parameterized procedure (for example, find every caller of a named symbol with citations) so the harness runs a `function_try` and procedural memory can start; a plan of one-off reading questions leaves the catalogue empty.

   Ask a simple question about how the mechanism works and request source references for the findings. Let the harness choose its investigation and memory procedures. You own the overall reasoning: assess whether each answer and its source references actually explain the question, including relevant conditions and relationships. A `complete` status or a citation to an earlier report alone does not establish that the source code answers it.

   Pass the actual absolute root and one question as separate, safely quoted arguments; do not interpolate user text into shell syntax. Wait for each JSON result before starting the next call. Use the same workspace so all calls share `.tours/.memory/`. If an essential part is unsupported or uncertain, request a targeted follow-up for that gap or explain the limitation, regardless of status. Retain partial or failed statuses and uncertainties; do not repeat a sufficient answer. Direct file reads are allowed for targeted verification; record what was checked and why. Substantial research belongs in the harness.
3. Assemble the answers into a coherent Tour: explain functional relationships and progression, preserve supporting file, line and revision references, and carry forward uncertainty. Do not invent anchors or promote incomplete results to complete evidence. Follow the `create_project_tour` tool's current schema and guidance. Give the Tour an ASCII slug as `fileName` (for example `memoire-procedurale_SKILL_4`) and keep the accented title in `title`. Put every Mermaid edge label in double quotes, since parentheses break validation. When an anchor pattern matches several lines, narrow it with the harness's cited line numbers. Call it without `dryRun` to write; correct any validation issues and retry. Use `dryRun: true` when validation without writing is needed. Report a `.tour` as created only when the write succeeds, and give its confirmed path so it can be opened in VS Code.
4. Produce a concise diagnostic report alongside the result, for example under `.tours/research-reports/`, correlating a unique Tour identifier and confirmed Tour path with each question identifier and CLI `runId`. For each run, report its status, relevant `callTrace` and `consolidationReport` observations: function identity, actual execution, validation, persistence or refusal, and the observed reason when present. Point to `.tours/.log/research.log` (a single size-rotated file, 10 MB × 10, not one file per run) and filter it by `runId` for details. Record the skill version or file revision, model, elapsed time, observed token counts and `usageAvailable`; label unavailable counters rather than adding an invented total. Avoid recording credentials; free text in logs is not guaranteed secret-free.
5. In that report separate observed facts, inferences and unmeasurable information. Use Copilot tool history to identify direct reads when available; otherwise mark direct research **not measurable**, never zero. Assess delegation separately from Tour quality: substantial research performed mainly outside the harness fails delegation even if a Tour was written. Structural citation validation establishes that lines exist, not that their interpretation is correct; identify semantic review as a separate check. For each persisted function, inspect its source and observed output when available: state the recurring question it addresses and the structured evidence it actually produces. Do not claim useful learning from persistence alone: require a later `memory_run` execution of the same identity and evidence that its output was relevant to the later question. Do not force a function into memory when none is useful. Include an honest outcome when evidence or telemetry is missing.
