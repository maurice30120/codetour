Un graphe compact remplace-t-il vraiment les lectures ?

On injecte dans le contexte un graphe de dépendances de 30–40 tokens au lieu de laisser l'agent lire les fichiers. Est-ce que ça économise des tokens — et est-ce que la réponse reste utile pour un Tour de review ?

La barre n'est pas « 100 % de toutes les relations ». Pour un Tour de review qui modifie une fonction, il faut que tous les appelants de cette fonction soient soit assertés, soit pointés (fichier + ligne + candidats). Le côté sortant peut rester partiel. Les quatre attitudes ci-dessous comparent le coût en tokens sous cette barre-là.

Ce que ce prototype ne prouve pas

  • Le baseline est une simulation. Il compte grep + lecture intégrale des fichiers qui mentionnent le nom, plafonné à 8 fichiers. Un agent réel lit parfois moins (s'il devine bien) ou plus.
  • Les tokens sont comptés avec gpt-tokenizer, pas avec le tokenizer exact de Claude ou Copilot. Les écarts absolus bougeront de quelques pourcents, pas l'ordre de grandeur.
  • Le graphe est celui de @codeflow-map/core 1.0.3 aujourd'hui. Une résolution inter-fichiers maison changerait les chiffres — c'est justement la piste B.
  • Les lignes « ? » sont une simulation de ce que le graphe pourrait dire. La bibliothèque jette ces appels ; le prototype les reconstitue à partir des mêmes RawCall qu'elle a déjà en main.
  • Un angle mort ne se pointe pas. Un nœud que l'extracteur n'a jamais vu (ex. diagramNodeCount) ne produit ni arête ni ligne « ? » : l'absence totale et l'absence locale sont indiscernables.
